# DX-018: Serverless throttling

[Catalog](../detectors.md) | [Access and sign-in](../permissions.md)

## Data and scope

Applies only to containers enumerated in an ARM `EnableServerless` account. Serverless
containers have no throughput offers and use a separate pipeline pass.
Production requests seven days of `TotalRequests` totals and 429 counts scoped by database
and collection. No Log Analytics is required.

## Detection and severity

| Configuration | Default |
|---|---|
| `throttle_rate_pct` | `1.0` |
| `severity_med_pct` | `5.0` |
| `severity_high_pct` | `20.0` |
| `min_total_requests` | `1000.0` |

At least 1,000 requests and a 429 rate of at least 1% produce a finding.
Severity is High at 20%, Medium at 5%, otherwise Low. Below 1% is not detected;
below 1,000 requests is insufficient data.

## Evidence and limits

With 1,000 requests, 10 throttles are Low, 50 are Medium and 200 are High.
One recent sample containing 1,000 requests and 250 throttles is sufficient for a
25%-rate High finding. **There is no minimum resource age or elapsed-history gate.**
The seven-day query range is not a requirement to wait seven days.

SDK retries can make application-visible errors much lower than server-side 429s.
This signal does not distinguish hot logical keys, bursts or broad demand, and it does
not measure an exact per-partition RU ceiling. The 5,000 RU/s per-partition value in the
recommendation is platform context, not a trigger or measured account capacity.
No requests abstain; access/query failures remain errors rather than healthy results.

## Remediation and references

The mapped rule is
[`throughput-serverless`](https://github.com/AzureCosmosDB/cosmosdb-agent-kit/blob/main/skills/cosmosdb-best-practices/rules/throughput-serverless.md).
Review workload shaping, partition distribution and current conversion/migration eligibility
before choosing provisioned capacity. There is no serverless provisioned-RU/s setting for CODA
to increase. CODA does not perform conversion.
