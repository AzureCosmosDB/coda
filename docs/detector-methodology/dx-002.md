# DX-002: Cross-partition query fan-out

[Catalog](../detectors.md) | [Log prerequisites](../detections/log-analytics-readiness.md)

## Data and scope

Evaluates containers, including the serverless pass. Production requests one day of
`CDBQueryRuntimeStatistics` and raw `CDBDataPlaneRequests` through account-resource queries.
The five-minute request aggregate is not a substitute for this raw request-charge join.
Unavailable prerequisites, insufficient records and failed queries must remain distinguishable.

Logical queries are grouped by correlated activity and query text. Distinct partition ranges
measure fan-out; request charge joins on activity ID provide RU evidence. The query keeps the
200 most frequent shapes. The widest observed fan-out estimates partition count; it is not
an authoritative inventory of every physical partition.

## Detection and severity

| Configuration | Default |
|---|---|
| `min_queries` | `50` |
| `cross_fanout_threshold` | `1.5` |
| `min_share_pct` | `10.0` |
| `min_rate_qps` | `0.1` |
| `high_rate_qps` | `1.0` |
| `medium_partitions` | `4` |
| `high_partitions` | `7` |

A shape averaging at least 1.5 partitions counts as cross-partition. At least 50 observed
executions, more than one observed partition, at least 10% cross-partition executions and
at least 0.1 fan-out executions per second are needed. The rate uses the actual window
duration. Below the rate floor is occasional fan-out, not a finding. **RU is not a gate.**

| Observed partitions | Rate below 1 query/s | Rate at least 1 query/s |
|---|---|---|
| 2-3 | Low | Low |
| 4-6 | Low | Medium |
| 7+ | Medium | High |

## Evidence and limits

### Show observations immediately; grade only after 24 hours

CODA reports the fan-out counts it can read, even for a newly created container.
It assigns severity only when the container existed and both required logging categories
were configured for the whole evaluation window, at least **24 elapsed hours**. Production
looks back at most 24 hours and never queries before known container creation. An explicit
shorter report is observation-only, however high the query rate.

| What the logs show | What CODA reports |
|---|---|
| An hour-old container has 1,000 queries touching four partitions. | 1,000 observed fan-out queries. No severity or change recommendation yet. |
| An older container has the same 1,000 queries and 23 quiet hours, with a full day of logging history. | About 0.012 fan-out queries/s: occasional fan-out, not a finding. |
| The full day has 24,000 such queries. | About 0.28/s. With the other existing checks satisfied, a **Low** query-investigation finding. |
| The container is old but query logging was enabled four hours ago, or its history cannot be verified. | Keep measured counts; withhold severity. A partial or failed log query is an incomplete check, not zero activity. |

Quiet hours count as elapsed time. CODA does **not** require a query in each hour or send
per-hour Azure Monitor probes. It uses same-container creation or last-modified evidence
as a lower bound on resource age, and current resource-specific diagnostic settings and
their last-modified timestamps as a lower bound on logging history. Recent edits can
conservatively delay grading even if they did not interrupt logging. An omitted setting
timestamp or denied settings read cannot certify a full day. This checks configuration
history and read success, **not** delivery of every event. A report finding suggests
investigating the query filter, not redesigning the container's partition key.

Use unrounded values for decisions: displayed percentages/rates can round onto a boundary.

Query text can be anonymized or contain sensitive text depending on logging; never assume
it is safe to send to another model. A shape is not proof of the original source-code query
or the correct partition key. Legitimate analytical fan-out can still meet these gates.
No/fewer-than-50 executions abstain. A reported query failure is not a clean result, even
where the detector's legacy reason token is `log_analytics_unavailable`.

**DX-002 asks whether a query can use the current partition key.** If the caller knows the
tenant ID and the container is partitioned by tenant, check that the request routes by that
ID. [DX-007 asks a different question](dx-007.md#dx-002-versus-dx-007-query-routing-or-data-design):
can the caller supply that key for the application's frequent lookups at all? Fan-out alone
cannot distinguish an omitted routing key from an intentional cross-tenant report.

## Remediation and references

Load
[`query-avoid-cross-partition`](https://github.com/AzureCosmosDB/cosmosdb-agent-kit/blob/main/skills/cosmosdb-best-practices/rules/query-avoid-cross-partition.md).
Review partition-key filters and access patterns; an ordinary index alone does not change
partition routing. Consider alternate models/indexing capabilities only after eligibility review.
DX-007 does not supersede this finding. In a mixed workload DX-007 can show a design-review
prompt without a separate severity; when a workload recurs
in at least three distinct hours spanning four or more elapsed hours within a verified day,
and every observed logical query fans out, it instead recommends re-keying
at High severity. A lone nightly report does not qualify.
CODA does not rewrite queries.
