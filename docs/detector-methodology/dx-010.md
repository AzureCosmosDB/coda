# DX-010: Throttling during write activity

[Catalog](../detectors.md) | [Log prerequisites](../detections/log-analytics-readiness.md)

If a batch writer and other requests run together, **which operations received server-side
429s during the write load?** DX-010 compares operations in the **same container and
completed UTC five-minute interval**. A short job on a new container can qualify on its
first interval. There is no minimum age, duration, request volume, or repeat count.

## Data and scope

The production lookback is one day. CODA uses one resource-specific Log Analytics source:
`CDBDataPlaneRequests5M` when available (`RequestCount` and `TotalRequestCharge`), otherwise
`CDBDataPlaneRequests` (one request per row and `RequestCharge`). Counts and RU are summed,
not averaged across records or added across tables. Each query limits the end exclusively,
uses one diagnostic destination and matches the exact account, database and container.
Both sources use five-minute intervals for grading. An explicitly unaligned 5M window
is rejected; for raw data only the completed five-minute bins inside the request are read.

**Write dominance** means writes consumed at least **80% of measured RU in that interval**.
It is a provisional proxy for write pressure, **not utilization of provisioned throughput**.
Create, Upsert, Replace, Delete, Patch, Batch and Execute form the writes group. Read, Head,
ReadFeed, HeadFeed, Query, QueryPlan and other identified service operations outside the
write set are assessed by name: successful queries, for example, do not dilute the
fraction of Read attempts throttled. Missing, malformed or unspecified operation labels
cannot establish non-write impact.

## Detection and severity

| Configuration | Default |
|---|---|
| `write_ru_pct_floor` | `80.0` |
| `min_throttled` | `10` |
| `throttle_rate_pct` | `10.0` |

With the write-share proxy met, an operation group qualifies when **at least 10 attempts**
received a server-side 429 **and at least 10% of that same group's attempts** were
throttled in the interval. Compare before rounding; 9 of 10 and 10 of 101 do not qualify.

| Measured interval | Report |
|---|---|
| 200 of 1,000 writes throttled; 0 of 1,000 reads throttled | **Medium**. Pace the writer. |
| 0 of 1,000 writes throttled; 200 of 1,000 reads throttled | **High**, including the first episode. |
| Both writes and reads materially throttled | **High**. |
| 10,000 successful writes and 10 of 100 reads throttled | **High**; measure reads against 100, not 10,100. |
| 10 of 10 writes throttled, all measured RU on writes | **Medium**; no 1,000-request floor. |
| 9 of 10 reads throttled, or material read 429s with only 79.999% write RU | Ungraded observation. Keep the counts. |
| Morning import succeeds; only reads run in the evening interval with 429s | Ungraded read observation. No advice to slow the morning import. |

## Evidence and limits

The report names the strongest supported interval and its operation counts. Structured
evidence retains every measured interval, including those below threshold. Absent intervals
are counted as unobserved, not as zero traffic. Missing status, attempt, RU or operation
attribution prevents grading that interval; it cannot erase an independent complete
interval. If some statuses are missing but 429s were recorded, the known count is a lower
bound, not an exact rate. Zero total RU is measured but has no defined write share. No
rows is insufficient data. A failed query or rows without a trustworthy container or time
assignment are not a clean result. A full grid of timestamps alone does not prove complete
collection.

Peak-to-average write RU (observed write buckets only: one minute raw, five minutes
aggregate) and the dominant write user-agent describe the **whole observation window**.
They are optional context, not gates or evidence that a specific client ran in an episode.

## Remediation and references

Pace the writer with bounded concurrency and honor retry-after. Depending on the SDK and
workload, consider priority-based execution or throughput buckets. **Only for a confirmed
Spark ingestion job**, consider Spark connector throughput control. See
[`sdk-ingestion-rate-control`](https://github.com/AzureCosmosDB/cosmosdb-agent-kit/blob/main/skills/cosmosdb-best-practices/rules/sdk-ingestion-rate-control.md).
Overlap does not prove the writer caused another operation's 429, and server-side throttling
does not prove an application request failed. CODA recommends; it changes no resources.
