# DX-007: Shard-key misalignment

[Catalog](../detectors.md) | [Shared fan-out signal](dx-002.md)

## Data and scope

Escalates widespread fan-out into a partition-key/access-pattern review for a container,
including serverless containers. It reuses DX-002's one-day query-statistics/raw-request-log
signal and data requirements; there is no separate observation of the correct key.
Both `CDBQueryRuntimeStatistics` and raw `CDBDataPlaneRequests` are required.

### DX-002 versus DX-007: query routing or data design?

| Detector | Question | Example: an `Orders` container partitioned by `/tenantId` |
|---|---|---|
| [DX-002](dx-002.md) | Can this query use the **existing** partition key? | A tenant dashboard already knows the tenant ID but doesn't pass it. Check the filter and the partition key supplied by the caller before considering a container change. |
| DX-007 | Does the existing key fit the way the application **usually looks up data**? | The checkout service repeatedly looks up an order by `orderId`. If the owner confirms the caller cannot know the tenant ID, compare ways to serve that lookup. A different partition key is only one option. |

A nightly finance report deliberately reading across tenants may use substantial RU without
indicating a bad key. Conversely, a lookup that costs little per execution can matter when
executed thousands of times. Use logical fan-out executions per measured time to describe
frequency, and total measured request charge for that query pattern over the **same period**
to describe cost. RU consumed is not proven waste, money spent, or a savings estimate.

DX-002's query-level finding stays visible. When both single-partition and fan-out queries
are observed, DX-007 shows a **design-review prompt with no separate DX-007 severity** if
the same lookup fans out at least twice with starts at least **one actual hour apart**.
It shows the frequency and measured charge and asks whether the caller can supply the key. This prompt does not add
a second graded finding, select a replacement key, or direct a migration. Container-wide
fan-out share is **context, not a veto**: a lookup executed 20,000 times and consuming
120,000 RU over a day is equally eligible for review whether it represents 80% or 10% of
the container's observed queries. That is an example, not a cutoff.

**Exception: every observed query fans out and the workload recurs within the day.**
DX-007 reports **High** and explicitly **recommends re-keying the container**. For
example, a container keyed by `/id` has a full day of query history. All 24,000 lookups
throughout the day touch multiple physical partitions. No single-partition query or
minimum RU cost is needed as a comparison. The owner chooses a replacement key that fits
the application; CODA does not migrate data. If the day's only query is one nightly
report, show the observation without severity or a re-key recommendation.

“Every” means every observed **logical query execution**, not every read operation: point
reads are not queries. One single-partition execution rules out this exception. A rounded
percentage, a per-shape average, or only the top 200 shapes cannot establish it. If some
executions cannot be classified, do not claim that every query fanned out.

Within a verified 24-hour window, require logical query **starts in at least three distinct
UTC hours**, with **at least four elapsed hours** between the first and last starts. The hours
need not be consecutive. For example, 08:00, 10:00 and 12:00 qualifies; 08:01, 10:00 and
12:00 does not. A long-running query counts once, not once per hour it was active.

## Detection and severity

| Configuration | Default |
|---|---|
| `min_start_hours` | `3` |
| `min_elapsed_hours` | `4` |

Only the recurring all-query case receives a severity. The detector evaluates at most the
last 24 hours of the requested window. Short or unverifiable resource/logging history cannot
authorize High. The classifier is a review policy, not a validated estimate of migration benefit.

## Evidence and limits

The first logged visit of each correlated execution is its observed start. Counts are
computed before selecting display examples. Mixed prompts group by logged SQL pattern
(not the parameter-value envelope) and retain up to 200 examples, prioritizing recurring
patterns and known total RU. Missing or ambiguous request charges are unknown, not zero.
An empty or failed query-log read does not prove that the key is aligned. Even recurring
fan-out can be intentional: CODA does not know which replacement key the application needs.

## Remediation and references

Use
[`partition-rekey-migration`](https://github.com/AzureCosmosDB/cosmosdb-agent-kit/blob/main/skills/cosmosdb-best-practices/rules/partition-rekey-migration.md)
to review access patterns and, if warranted, a new-container/backfill/cutover plan. Do not
make a migration decision from anonymized query shapes alone. CODA never migrates data.
