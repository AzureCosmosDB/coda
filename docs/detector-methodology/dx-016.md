# DX-016: Expensive consistency

[Catalog](../detectors.md) | [Log prerequisites](../detections/log-analytics-readiness.md)

## Data and scope

An account-level review of ARM default consistency and region count. It is not a measurement
that the application can safely use weaker guarantees. Optional request-log enrichment
does not determine whether the configuration finding exists.
An account has **one default consistency level**: Strong **or** Bounded Staleness are alternative
settings, not simultaneous requirements. Each row below describes a separate account configuration.

## Detection and severity

| Default consistency and regions | Result |
|---|---|
| Strong in one region | Medium |
| Strong across at least two regions | Medium |
| Bounded Staleness across at least two regions | Low |
| Bounded Staleness in one region | Not detected |
| Session, Eventual or Consistent Prefix | Not detected |
| Missing consistency level | Unknown; do not infer a relaxed configuration |

Enum-qualified values, underscores and casing are normalized. The configuration decision
uses the current snapshot, not a historical utilization window.

"Premium" in older/internal labels is shorthand for Strong or Bounded Staleness consistency,
**not an Azure pricing SKU or service tier**. Reads using these levels use a local replica
quorum and cost twice the RU of Session reads. Strong therefore merits review even in one
region. Cross-region write latency is a separate multi-region trade-off, not a single-region
cost. The existing policy still excludes single-region Bounded Staleness; that is not a claim
that its reads have no RU overhead. An unknown region count is not assumed to be one region.

## Evidence and limits

Optional enrichment requests 24 hours of exact-account request charge for **Read, Query and
QueryPlan** only. It prefers `CDBDataPlaneRequests5M`, retaining raw
`CDBDataPlaneRequests` compatibility. Absolute bounds are start-inclusive/end-exclusive;
aggregate requests are represented counts, not table-row counts.

If observed accumulated read charge is `R` RU, the avoidable quantity is at most `R / 2`.
For 200 RU, 100 RU is an **upper bound**, not a measured saving: per-request consistency
overrides and the application's required guarantees are unknown. This is accumulated RU,
not RU/s, and it produces neither generic recoverable capacity nor a dollar estimate.

Missing logs, no matching observations, malformed aggregates or failed enrichment preserve
the qualitative ARM finding with explicit unavailable/no-observations evidence. They are not
zero measured cost and do not justify enabling every logging category. ReadFeed and Head are excluded.
Review the explicit incomplete-evidence details.

## Remediation and references

Use
[`global-consistency`](https://github.com/AzureCosmosDB/cosmosdb-agent-kit/blob/main/skills/cosmosdb-best-practices/rules/global-consistency.md)
to assess correctness, consistency, latency and availability requirements. CODA never relaxes
consistency automatically.

If application requirements permit, evaluate Session. It provides **read-your-writes within
a session** when the relevant session token is preserved. A reused SDK client caches and sends
tokens automatically for its session. In a load-balanced web application, use the documented
end-user round trip:

1. Capture the `SessionToken` from the Cosmos response and return it through the web tier to
   the end-user client in a cookie (or equivalent client context).
2. Receive that token on a later web request.
3. Pass the relevant token in the Cosmos request options of whichever SDK instance handles
   that request.

This does not require direct SDK-to-SDK synchronization. Tokens are **opaque and partition-bound**:
use the latest token for the relevant items and do not modify it. This is application guidance,
not cookie handling or authentication implemented by CODA.

Session is **not equivalent to Strong's global guarantees** across all clients. Check the
application's correctness requirements and current per-request consistency overrides before
changing the default. Weaker read overrides do not change a Strong account's write replication.
