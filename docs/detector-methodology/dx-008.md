# DX-008: Multi-region writes antipattern

[Catalog](../detectors.md) | [Access and sign-in](../permissions.md)

## Data and scope

Account-configuration review using ARM multi-write enablement, API family, write-region count,
region count and environment signals. It does not infer a need for high availability from
where application writes happened. Public web discovery targets NoSQL; the engine also
retains non-NoSQL API guards for programmatic inputs.

Environment classification uses normalized tags and subscription/account-name signals with
boundary-aware matching. A specific non-production account signal can override a broad
production subscription name; unknown environment is treated conservatively as production.
An inferred environment is evidence to verify with the owner, not a policy decision.

## Detection and severity

Apply these branches in order:

| Configuration | Result |
|---|---|
| Multi-region writes disabled | Not detected |
| Multi-write on MongoDB, Cassandra, Gremlin or Table API | High API-compatibility review |
| Multi-write with fewer than two write regions | Low tripwire, including production |
| Multi-write with at least two write regions in production/unknown environment | Not detected |
| Multi-write with at least two write regions in positively classified non-production | Medium |

This is point-in-time configuration, with no workload-history gate.

## Evidence and limits

Only complete, unique, positive, all-manual throughput offers can quantify regional capacity.
Shared database offers are counted once. If per-region allocation is `S` and the account
has `N` regions, the footprint is `S * N`. Removable extra-region capacity `S * (N - 1)`
is attributed only to the non-production region-removal recommendation. Serverless, empty,
duplicate, invalid, mixed or autoscale inventory is unquantified, not zero.

For `S = 4,000 RU/s` and three regions, footprint is 12,000 regional RU/s and the
non-production extra-region quantity is 8,000. **Disabling multi-write while retaining
the regions does not remove that footprint.**

Optional currency enrichment requires a valid customer-amortized-bill rate and qualifying
removable capacity. A successful account billing read with no usable rate may use a labelled
subscription fallback; a failed account read does not. No retail-rate fallback or blanket
bill reduction is asserted. Unavailable enrichment does not erase the configuration finding.
