# DX-008: Multi-region writes antipattern

[Catalog](../detectors.md) | [Access and sign-in](../permissions.md)

## Data and scope

Account-configuration review using ARM multi-write enablement, API family, write-region count,
region count and environment signals. It does not infer a need for high availability from
where application writes happened. Public web discovery targets NoSQL; the engine also
retains non-NoSQL client advisories for programmatic inputs.

Environment classification uses normalized tags and subscription/account-name signals with
boundary-aware matching. A specific non-production account signal can override a broad
production subscription name; unknown environment is treated conservatively as production.
An inferred environment is evidence to verify with the owner, not a policy decision.

## Detection and severity

Apply these branches in order:

| Configuration | Result |
|---|---|
| Multi-region writes disabled | Not detected |
| Multi-write on MongoDB, Cassandra, Gremlin or Table API | Low: verify how this application redirects writes during a regional outage |
| Multi-write with fewer than two write regions | Low tripwire, including production |
| Multi-write with at least two write regions in production/unknown environment | Not detected |
| NoSQL multi-write with at least two write regions in positively classified non-production | Ungraded configuration review; report the verified footprint |

This is point-in-time configuration, with no workload-history gate.

**One writable region (NoSQL):** recommend disabling multi-region writes now, in any
environment. There is no second region to accept writes. If a team later adds a region
with the setting still enabled, provisioned throughput can be billed at the multi-region
write rate. This Low finding flags a future cost risk, not savings on today's bill.
Disabling the setting does not remove a region or its provisioned throughput.

**Two or more writable regions (non-production NoSQL):** CODA shows an ungraded review prompt.
The label does not tell CODA whether the team rehearses failover there. For example,
4,000 manual RU/s per region in two regions is an 8,000 regional RU/s footprint when
inventory is complete. None of that capacity is known to be removable; do not claim
savings even if a matching bill rate is available. If capacity cannot be quantified,
the prompt still reports the writable-region topology.

### What client failover means for each API

An account can accept writes in two regions without a particular application knowing how to
switch between them. For example, writes may succeed locally in both East and West, but that
does not show that an application using East can resume writes in West during an East outage.

| API | What the application owner should verify |
|---|---|
| [MongoDB](https://learn.microsoft.com/en-us/azure/cosmos-db/mongodb/how-to-configure-multi-region-write) | Cosmos DB supports active-active writes. The connection's `appName` can select a preferred write region; that preference alone is not a failover test. |
| [Cassandra](https://learn.microsoft.com/en-us/azure/cosmos-db/cassandra/driver-extensions) | The default DataStax Java v4 policy uses one local datacenter. The Cosmos driver extension can be configured with preferred regions for outage failover. Check the actual driver and policy. |
| [Gremlin](https://learn.microsoft.com/en-us/azure/cosmos-db/gremlin/use-regional-endpoints) | Regional endpoints can accept writes when configured as writable. Cosmos updates the global endpoint's DNS during service-side write-region failover; a client pinned to a regional endpoint needs its own rerouting strategy. |
| [Table](https://learn.microsoft.com/en-us/azure/cosmos-db/table/tutorial-global-distribution) | The Cosmos Table SDK tutorial documents local writes and automatic fallback with `CosmosExecutorConfiguration.CurrentRegion`. Verify the SDK and version in use; this is not a guarantee for every Table client. |

CODA does not inspect drivers, connection settings or outage-test results. **Low means verify,
not that failover is broken, multi-region writes are unsupported, or regions should be removed.**

## Evidence and limits

A missing ARM allocation prevents regional footprint quantification, but does not
erase an independently established account-configuration finding. Count the database pool once
and each dedicated sibling once; do not count inherited members as additional reservations.

Only complete, unique, positive, all-manual throughput offers can quantify regional capacity.
Shared database offers are counted once. If per-region allocation is `S` and the account
has `N` regions, the footprint is `S * N`. Serverless, empty,
duplicate, invalid, mixed or autoscale inventory is unquantified, not zero.

For `S = 4,000 RU/s` and three regions, footprint is 12,000 regional RU/s. That is
configured capacity, not recoverable capacity. **Disabling multi-write while retaining
the regions does not remove that footprint.**

DX-008 does not contribute recoverable RU/s or dollars to report totals.

## Remediation and references

For the single-write-region NoSQL recommendation, use
[`global-multi-region-write-antipattern`](https://github.com/AzureCosmosDB/cosmosdb-agent-kit/blob/main/skills/cosmosdb-best-practices/rules/global-multi-region-write-antipattern.md).
Confirm availability, failover, conflict and environment requirements before removing regions
or changing multi-write. The API-only advisory instead asks for a controlled client failover
test; it does not link to a disable-multi-write rule or claim savings. CODA makes no changes.
