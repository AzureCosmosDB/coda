# DX-020: Non-throttling errors

[Catalog](../detectors.md) | [Access and sign-in](../permissions.md)

## Data and scope

Account-level Azure Monitor `TotalRequests`, split by `StatusCode` with Count aggregation.
Production requests seven days at hourly grain; no Log Analytics is needed.
Only parseable status/count pairs with positive counts participate.

## Detection and severity

**Threshold status: proposal.** The current defaults are ranking heuristics, not an assurance
that these error rates are appropriate for every workload.

| Configuration | Default |
|---|---|
| `MIN_TOTAL_REQUESTS` | `1000` |
| `HARD_ERROR_RATE_PCT` | `1.0` |
| `SEVERITY_MEDIUM_PCT` | `5.0` |
| `SEVERITY_HIGH_PCT` | `10.0` |

Hard errors have a numeric status at least 400, excluding 429. Divide their count by
**all parsed requests, including 429s**. At least 1,000 requests and at least 1% hard
errors produce a finding: High at 10%, Medium at 5%, otherwise Low.
The most frequent hard-error status and per-status rates are reported.

## Evidence and limits

For 1,000 requests, 9 hard errors are below the gate, 10 are Low, 50 are Medium and
100 are High. 400 throttles alone produce a zero hard-error numerator, not a finding here.
Fewer than 1,000 requests abstain. Service/read failures are errors.

404s and concurrency-related statuses can be intentional. The dominant code guides an
investigation; it does not prove a bug, a missing role, or a particular firewall setting.
5xx can be service-side, not necessarily client-side. This check is account-level and does
not identify the responsible container, application, operation or item. Status counts alone
cannot establish a read-404-then-insert sequence. The action and evidence retain this limitation;
selecting a rule does not mean its antipattern has been detected.

## Remediation and references

Only detected findings with these dominant statuses receive conditional guidance:

| Dominant status | Agent Kit rule |
|---|---|
| 404 | `sdk-conditional-create-etag` |
| 409 | `sdk-conditional-create-etag` |
| 412 | `sdk-etag-concurrency` |
| Other statuses | null |
| Not detected or abstained | null |

**404 or 409:** review
[`sdk-conditional-create-etag`](https://github.com/AzureCosmosDB/cosmosdb-agent-kit/blob/main/skills/cosmosdb-best-practices/rules/sdk-conditional-create-etag.md)
as a conditional investigation. Check expected missing-item lookups and the correct id and
partition-key context. **Only if** application code or traces confirm existence-check-before-create,
evaluate SDK-appropriate atomic create and appropriate 409 conflict handling. Unconditional upsert
is not equivalent to create-if-absent: it can overwrite existing data. A 404 does not supply the
missing item's ETag.

The rule's example is **Java-specific**, not a universal header requirement. In the .NET SDK,
[`IfNoneMatchEtag` is ignored for writes](https://learn.microsoft.com/en-us/dotnet/api/microsoft.azure.cosmos.requestoptions.ifnonematchetag?view=azure-dotnet);
do not assume its wildcard provides create protection. Use the actual SDK's atomic-create and
conflict semantics.

**412:** review
[`sdk-etag-concurrency`](https://github.com/AzureCosmosDB/cosmosdb-agent-kit/blob/main/skills/cosmosdb-best-practices/rules/sdk-etag-concurrency.md)
and inspect the actual operation and ETag/precondition handling. A 412 can be expected protection
working, **not proof of missing concurrency control or a hot item**. For a confirmed read-modify-write
path, re-read current state and its ETag, reapply the intended update, and retry with bounded attempts.
Surface unresolved conflicts rather than dropping preconditions or blindly replaying stale state.

**Other statuses:** no concurrency rule is forced onto authentication, service or other errors.
Review request validation, access, configuration, retries or service health as appropriate.
Increasing throughput is not a general remedy for non-429 failures. CODA does not change
application code or permissions.
