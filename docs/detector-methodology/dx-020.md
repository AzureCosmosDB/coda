# DX-020: Non-throttling errors

[Catalog](../detectors.md) | [Access and sign-in](../permissions.md)

## Data and scope

Read account `TotalRequests` from Azure Monitor, split by `StatusCode` with Count aggregation,
over seven days. Keep each hourly bucket separate. No Log Analytics is required.

## Detection and severity

| Configuration | Default |
|---|---|
| `MIN_TOTAL_REQUESTS` | `1000` |
| `HARD_ERROR_RATE_PCT` | `1.0` |
| `SEVERITY_MEDIUM_PCT` | `5.0` |
| `SEVERITY_HIGH_PCT` | `10.0` |

Grade **5xx alone** in a completed UTC hour with at least 1,000 requests: Low at 1%,
Medium at 5%, High at 10%, inclusive. Divide by all requests in that hour, including 429s.
These are proposed incident-review thresholds, not a service-level objective.
Partial or low-volume intervals remain descriptive. The report retains counts and
rates by non-429 error status in each affected interval, and highlights the worst graded hour.

## Evidence and limits

Of 1,000 attempts, 400 returned 404 and 10 returned 503. Show 40% 404 and 1% 503;
the 5xx grade is **Low**, not High. A million successes the following hour do not erase it.
If there were only the 404s, the observation would be visible without a graded issue.

All non-429 4xx responses remain ungraded without independent corroboration. A 404
lookup miss, 409 conflict or 412 precondition failure can be expected behavior.
These are server responses, not failed user requests.

## Remediation and references

Check actual intent and SDK diagnostics;
counts alone identify neither the responsible item/operation nor a cause. No status-only
Agent Kit fix is selected. HTTP 429s belong to the throttling checks.
